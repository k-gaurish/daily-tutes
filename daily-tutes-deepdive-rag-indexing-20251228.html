The Indexing Problem: Why Basic Chunking Fails

In Parts 1-11, we learned the basic RAG pipeline: Load → Split → Embed → Store → Retrieve → Generate. But there's a fundamental problem with this approach that becomes painfully obvious in production systems.

📚 Analogy: The Library Index Problem

Imagine you're a librarian creating a card catalog for a massive library. The basic approach is like writing one index card for every 3 pages of every book. When someone asks about "World War II tanks," you find cards mentioning tanks. But what if the question is "What was the overall impact of mechanized warfare on 20th-century conflicts?" — a broader question requiring synthesis across multiple books and chapters. Your 3-page cards can't answer that because they're too granular!

The Three Core Problems with Basic Chunking

🔍
Problem 1: Embedding Dilution
A single vector trying to represent a 1000-word chunk loses nuance. Irrelevant content dilutes the semantic signal.
🌲
Problem 2: No Hierarchy
Flat indexing can't answer high-level "thematic" questions that require synthesizing information across multiple documents.
🎯
Problem 3: Lost Context
Small chunks are great for precision but terrible for context. You find the sentence but lose the paragraph that explains it.
📊 The Fundamental Trade-off

🎯 What You'll Learn in This Deep Dive

By the end, you'll understand three advanced indexing strategies that solve the chunk size trade-off in different ways:

  1. Multi-Representation Indexing: Index optimized representations (summaries/propositions), but return full documents
  2. RAPTOR: Build a hierarchical tree of summaries for both detailed AND thematic questions
  3. ColBERT: Use token-level embeddings for fine-grained matching without losing context

Multi-Representation Indexing (Part 12)

The core idea is elegantly simple: what you index for search doesn't have to be what you return to the LLM.

📚 Analogy: The Movie Trailer Approach

Think of movie trailers. When you search for a movie to watch, you don't search through the entire 2-hour film. You watch the 2-minute trailer (optimized for discovery). But when you actually want to watch, you get the full movie (complete context). Multi-Representation Indexing works the same way: create optimized "trailers" (summaries) for search, but return the full "movie" (document) to the LLM.

With Multi-Representation:

  • Create 1 summary per case = 10,000 summaries to search
  • Summaries focus on key facts, rulings, precedents
  • Return full case document for comprehensive LLM analysis

Propositions: The Dense X Retrieval Approach

The "Dense X Retrieval" paper (Chen et al., 2023) introduced a powerful alternative to summaries: propositions. Instead of summarizing, you decompose documents into atomic, self-contained facts.

📚 Analogy: Wikipedia Infobox vs Full Article

Think of a Wikipedia article about Albert Einstein. The full article is 10,000 words. But the infobox on the right has discrete facts: "Born: March 14, 1879", "Known for: Theory of Relativity", "Nobel Prize: 1921". Each fact is a proposition — self-contained and searchable. When someone asks "When was Einstein born?", matching the proposition is easier than matching the whole article.

What is a Proposition?

📋 Definition

A proposition is an atomic expression of meaning with three properties:

  1. Atomic: Cannot be split into smaller propositions
  2. Self-contained: Includes all necessary context (no pronouns like "it", "they")
  3. Factoid: Expresses a single, distinct fact

The Proposition Prompt

Prompt Template 
Decompose the "Content" into clear and simple propositions, ensuring 
they are interpretable out of context.

1. Split compound sentences into simple sentences. Maintain the 
   original phrasing from the input whenever possible.

2. For any named entity that is accompanied by additional descriptive 
   information, separate this information into its own distinct 
   proposition.

3. Decontextualize the proposition by adding necessary modifiers to 
   nouns or entire sentences and replacing pronouns (e.g., "it", 
   "he", "she", "they", "this", "that") with the full name of the 
   entities they refer to.

4. Present the results as a list of strings, formatted in JSON.

Content: {content}

💡 Key Insight: Information Density

Given a fixed token budget (say 500 tokens), you can fit ~10 propositions vs ~2 passages. This means your LLM gets 5x more relevant facts for the same context window cost!

Python - Multi-Vector Retriever with Propositions 
import uuid
from langchain.retrievers.multi_vector import MultiVectorRetriever
from langchain.storage import InMemoryStore
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

# 1. Create the two stores
vectorstore = Chroma(
    collection_name="propositions",
    embedding_function=OpenAIEmbeddings()
)
docstore = InMemoryStore()  # Stores full documents

# 2. Create retriever with ID linkage
id_key = "doc_id"
retriever = MultiVectorRetriever(
    vectorstore=vectorstore,
    docstore=docstore,
    id_key=id_key
)

# 3. For each document, generate propositions
for doc in documents:
    doc_id = str(uuid.uuid4())
    
    # Generate propositions using LLM
    propositions = generate_propositions(doc.page_content)
    
    # Create sub-documents for each proposition
    prop_docs = [
        Document(
            page_content=prop,
            metadata={id_key: doc_id}  # Link to parent!
        )
        for prop in propositions
    ]
    
    # Store propositions in vector store
    retriever.vectorstore.add_documents(prop_docs)
    
    # Store full document in doc store
    retriever.docstore.mset([(doc_id, doc)])

# 4. Query - searches propositions, returns full docs!
results = retriever.invoke("When was the Transformer introduced?")

Parent Document Retrieval: The Simpler Alternative

If generating propositions with an LLM feels too expensive, there's a simpler approach: Parent Document Retrieval. It uses the same two-store architecture but with simple chunking instead of LLM-generated propositions.

📚 Analogy: Book Chapter Sections

Imagine a textbook chapter (the "parent"). You split it into paragraphs (the "children") and index each paragraph. When someone searches, you find the most relevant paragraph, but you return the ENTIRE chapter so they get full context. The paragraph tells you WHERE to look; the chapter provides the WHY and HOW.

📊 Parent Document Architecture

    ┌─────────────────────────────────────────────────────────────┐
    │                                                             │
    │  "Machine learning is a subset of AI... [3000 words]"       │
    │                                                             │
    │    Split into CHILD CHUNKS (400 chars each)                 │
    │                                                             │
    │    ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐          │
    │    │ Child  │  │ Child  │  │ Child  │  │ Child  │   ...    │
    │    │   1    │  │   2    │  │   3    │  │   4    │          │
    │    └───┬────┘  └───┬────┘  └───┬────┘  └───┬────┘          │
    │        │           │           │           │                │
    │        │           │           │           │                │
    │        └───────────┴─────┬─────┴───────────┘                │
    │                          │                                  │

    │                   PARENT via doc_id                         │
    │                                                             │

                        RETRIEVAL FLOW
    
    Query: "What is supervised learning?"

    ┌───────────────────────────┐
    │ Search CHILD chunks       │◄── Find Child 3 matches best
    └─────────────┬─────────────┘

Two Modes of Parent Document Retrieval

📄 Mode 1: Return Full Document

Use when: Documents are reasonably sized (1-5 pages)

How: Only define child_splitter; the "parent" is the original document

Benefit: Maximum context for LLM

📑 Mode 2: Return Larger Chunks

Use when: Documents are very long (10+ pages)

How: Define both parent_splitter (larger) and child_splitter (smaller)

Benefit: Balanced context without overwhelming LLM

Python - Parent Document Retriever 
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_chroma import Chroma
from langchain_text_splitters import RecursiveCharacterTextSplitter

# MODE 1: Child chunks → Full document
child_splitter = RecursiveCharacterTextSplitter(chunk_size=400)

vectorstore = Chroma(
    collection_name="parent_doc_full",
    embedding_function=OpenAIEmbeddings()
)
store = InMemoryStore()

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=store,
    child_splitter=child_splitter  # No parent_splitter = return full doc
)

# Add documents
retriever.add_documents(documents)

# Query - searches 400-char chunks, returns FULL documents
results = retriever.invoke("What is machine learning?")
print(len(results[0].page_content))  # Full document length!
Python - Two-Level Parent Document Retriever 
# MODE 2: Child chunks → Larger parent chunks (not full doc)
parent_splitter = RecursiveCharacterTextSplitter(chunk_size=2000)
child_splitter = RecursiveCharacterTextSplitter(chunk_size=400)

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=store,
    parent_splitter=parent_splitter,  # Creates 2000-char parents
    child_splitter=child_splitter      # Indexes 400-char children
)

# Now:
# - Search is on 400-char chunks (precise)
# - Return is 2000-char chunks (contextualized)
🌍 Real-World Example: E-commerce Product Catalog

An online store has 50,000 product pages, each with title, description, specs, and reviews.

  • Child chunks: Individual paragraphs from description, each spec, each review
  • Parent document: Full product page
  • Query: "laptop with good battery life for travel"
  • Child match: "12-hour battery life, perfect for long flights"
  • Return: Full product page with price, specs, reviews, etc.

RAPTOR: Hierarchical Tree Indexing (Part 13)

RAPTOR (Recursive Abstractive Processing for Tree-Organized Retrieval) solves a problem that Multi-Representation can't: answering questions that require synthesizing information across MULTIPLE documents.

📚 Analogy: The Corporate Org Chart

Imagine a company with 1,000 employees. If someone asks "Who manages the sales team in New York?", you can find the specific person (low-level question). But if they ask "What's the company's overall strategy?", you need to understand how all departments work together (high-level question).

RAPTOR builds an "org chart" for your documents: individual paragraphs at the bottom, grouped into topic summaries, which are grouped into chapter summaries, all the way up to document-level themes. Now you can answer BOTH specific AND thematic questions!

The RAPTOR Algorithm: Step by Step

1
Embed All Chunks
Start with your original document chunks. Create embeddings for each chunk using your embedding model (e.g., OpenAI text-embedding-3-small).
2
Cluster Similar Chunks
Use Gaussian Mixture Models (GMM) with UMAP dimensionality reduction to cluster semantically similar chunks. GMM allows "soft" clustering where a chunk can belong to multiple clusters (important for multi-topic content).
3
Summarize Each Cluster
Use an LLM to generate a summary of all chunks in each cluster. This summary becomes a new "node" one level up in the tree.
4
Repeat Recursively
Take the summaries from Step 3, embed them, cluster them, and summarize again. Repeat until you reach a single root summary or a predefined depth.
5
Index ALL Levels
Store ALL nodes (original chunks + all summaries) in a single vector store. This allows retrieval at any level of abstraction.
💡 Key Insight: Soft Clustering with GMM

Unlike K-means (which assigns each chunk to exactly one cluster), GMM allows a chunk to partially belong to multiple clusters. This is crucial because a paragraph about "neural network training" might be relevant to both "machine learning algorithms" AND "computational resources" topics.

RAPTOR Implementation Deep Dive

Core Components

📊 RAPTOR Processing Pipeline
    ┌─────────────────────────────────────────────────────────────────┐
    │                      RAPTOR PIPELINE                            │
    └─────────────────────────────────────────────────────────────────┘
    
    STEP 1: EMBEDDING
    ┌──────────────────────────────────────────────────────────┐
    │  chunks = ["Text 1...", "Text 2...", "Text 3...", ...]   │
    │                          │                                │
    │                          ▼                                │
    │  embeddings = embed(chunks)  → [1536-dim vectors]         │
    └──────────────────────────────────────────────────────────┘
                               │
                               ▼
    STEP 2: DIMENSIONALITY REDUCTION (UMAP)
    ┌──────────────────────────────────────────────────────────┐
    │  1536 dimensions → 10 dimensions                          │
    │                                                           │
    │  Why? GMM works better in lower dimensions                │
    │  UMAP preserves local + global structure                  │
    │                                                           │
    │  Parameters:                                              │
    │    n_neighbors = 10  (local structure)                    │
    │    n_components = 10 (output dimensions)                  │
    │    metric = "cosine" (similarity measure)                 │
    └──────────────────────────────────────────────────────────┘
                               │
                               ▼
    STEP 3: CLUSTERING (GMM + BIC)
    ┌──────────────────────────────────────────────────────────┐
    │  GMM = Gaussian Mixture Model                             │
    │                                                           │
    │  For k in range(1, max_clusters):                         │
    │      fit GMM with k clusters                              │
    │      calculate BIC score                                  │
    │                                                           │
    │  Select k with best BIC (Bayesian Info Criterion)         │
    │                                                           │
    │  BIC balances:                                            │
    │    - Model fit (how well clusters explain data)           │
    │    - Complexity penalty (avoid over-clustering)           │
    └──────────────────────────────────────────────────────────┘
                               │
                               ▼
    STEP 4: SUMMARIZATION
    ┌──────────────────────────────────────────────────────────┐
    │  For each cluster:                                        │
    │      combined_text = join all chunks in cluster           │
    │      summary = LLM.summarize(combined_text)               │
    │                                                           │
    │  Prompt: "Summarize the following documents into a        │
    │           comprehensive summary..."                        │
    └──────────────────────────────────────────────────────────┘
                               │
                               ▼
    STEP 5: RECURSE
    ┌──────────────────────────────────────────────────────────┐
    │  if len(summaries) > 1:                                   │
    │      repeat steps 1-4 with summaries as input             │
    │                                                           │
    │  Build tree structure:                                    │
    │      Level 0: original chunks                             │
    │      Level 1: cluster summaries                           │
    │      Level 2: summary of summaries                        │
    │      ...                                                  │
    │      Level N: root summary                                │
    └──────────────────────────────────────────────────────────┘

Python - RAPTOR Core Functions 
import numpy as np
import umap
from sklearn.mixture import GaussianMixture
from langchain_openai import OpenAIEmbeddings, ChatOpenAI

# Initialize models
embd = OpenAIEmbeddings()
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def embed_texts(texts):
    """Embed list of texts into vectors."""
    return np.array(embd.embed_documents(texts))

def reduce_dimensions(embeddings, dim=10):
    """Reduce embedding dimensions with UMAP."""
    reducer = umap.UMAP(
        n_neighbors=10,
        n_components=dim,
        metric="cosine"
    )
    return reducer.fit_transform(embeddings)

def get_optimal_clusters(embeddings, max_k=50):
    """Find optimal number of clusters using BIC."""
    best_bic = float('inf')
    best_k = 1
    
    for k in range(1, min(max_k, len(embeddings))):
        gmm = GaussianMixture(n_components=k, random_state=42)
        gmm.fit(embeddings)
        bic = gmm.bic(embeddings)
        
        if bic < best_bic:
            best_bic = bic
            best_k = k
    
    return best_k

def cluster_embeddings(embeddings, n_clusters):
    """Cluster embeddings using GMM."""
    gmm = GaussianMixture(n_components=n_clusters, random_state=42)
    gmm.fit(embeddings)
    return gmm.predict(embeddings)

def summarize_cluster(texts):
    """Generate summary for a cluster of texts."""
    combined = "\n\n".join(texts)
    prompt = f"""Summarize the following documents into a coherent summary 
that captures the key information:

{combined}

Summary:"""
    return llm.invoke(prompt).content

def build_raptor_tree(texts, max_depth=3):
    """Build the complete RAPTOR tree."""
    all_nodes = []
    current_level = texts
    
    for level in range(max_depth):
        print(f"Building Level {level}...")
        
        # Store current level nodes
        all_nodes.extend([
            {"text": t, "level": level}
            for t in current_level
        ])
        
        # Stop if only one node left
        if len(current_level) <= 1:
            break
        
        # Embed and reduce dimensions
        embeddings = embed_texts(current_level)
        reduced = reduce_dimensions(embeddings)
        
        # Find optimal clusters and cluster
        n_clusters = get_optimal_clusters(reduced)
        labels = cluster_embeddings(reduced, n_clusters)
        
        # Summarize each cluster
        next_level = []
        for cluster_id in range(n_clusters):
            cluster_texts = [
                current_level[i] 
                for i, label in enumerate(labels) 
                if label == cluster_id
            ]
            if cluster_texts:
                summary = summarize_cluster(cluster_texts)
                next_level.append(summary)
        
        current_level = next_level
        print(f"  Created {len(next_level)} summaries")
    
    return all_nodes

# Build the tree
tree_nodes = build_raptor_tree(document_chunks)

# Index ALL nodes for retrieval
vectorstore = Chroma.from_texts(
    texts=[node["text"] for node in tree_nodes],
    embedding=OpenAIEmbeddings()
)

Retrieval Strategies

Strategy How It Works Best For
Tree Traversal Start at root, follow relevant branches down When you need to progressively narrow focus
Collapsed Tree Flatten tree, search all nodes at once (recommended) Most use cases — simpler and effective
⚠️ RAPTOR Cost Considerations

RAPTOR requires LLM calls to generate summaries at each level. For a corpus of 1000 chunks clustered into 100 → 10 → 1, you need ~111 summary generations. Factor this into your indexing budget.

ColBERT: Token-Level Embeddings (Part 14)

ColBERT (Contextualized Late Interaction over BERT) takes a completely different approach. Instead of creating better representations BEFORE indexing, it creates more GRANULAR representations that preserve nuance.

📚 Analogy: The Fingerprint vs Photo ID

Traditional embeddings are like a photo ID — one image represents your entire face. If someone has similar overall features, they might match. ColBERT is like a fingerprint — it captures EVERY detail (every ridge and whorl). When matching, it compares ridge-by-ridge for much higher accuracy.

In RAG terms: traditional embeddings create ONE vector for a whole chunk. ColBERT creates one vector FOR EACH TOKEN, then matches token-by-token for precise retrieval.

The MaxSim Operator: How ColBERT Matches

ColBERT's secret sauce is the MaxSim (Maximum Similarity) operator. Here's exactly how it works:

📊 MaxSim Calculation Step-by-Step
    QUERY: "river bank erosion"
    ┌───────────────────────────────────────┐
    │  Tokens: [river] [bank] [erosion]     │
    │  Embeddings: [q1] [q2] [q3]           │
    └───────────────────────────────────────┘

    DOCUMENT: "The bank of the river was muddy"
    ┌───────────────────────────────────────────────────────────┐
    │  Tokens: [The] [bank] [of] [the] [river] [was] [muddy]    │
    │  Embeddings: [d1] [d2] [d3] [d4] [d5] [d6] [d7]           │
    └───────────────────────────────────────────────────────────┘

    STEP 1: For each QUERY token, compute similarity with ALL doc tokens
    
    Query token "river" (q1):
    ┌────────────────────────────────────────────────────────────────┐
    │  sim(q1, d1) = 0.12  (The)                                     │
    │  sim(q1, d2) = 0.34  (bank)                                    │
    │  sim(q1, d3) = 0.08  (of)                                      │
    │  sim(q1, d4) = 0.11  (the)                                     │
    │  sim(q1, d5) = 0.91  (river) ◄── MAXIMUM!                      │
    │  sim(q1, d6) = 0.15  (was)                                     │
    │  sim(q1, d7) = 0.22  (muddy)                                   │
    │                                                                │
    │  MaxSim(q1) = 0.91                                             │
    └────────────────────────────────────────────────────────────────┘

    Query token "bank" (q2):
    ┌────────────────────────────────────────────────────────────────┐
    │  sim(q2, d1) = 0.09  (The)                                     │
    │  sim(q2, d2) = 0.88  (bank) ◄── MAXIMUM!                       │
    │  sim(q2, d3) = 0.11  (of)                                      │
    │  sim(q2, d4) = 0.10  (the)                                     │
    │  sim(q2, d5) = 0.45  (river) ← Some similarity (related)       │
    │  sim(q2, d6) = 0.13  (was)                                     │
    │  sim(q2, d7) = 0.19  (muddy)                                   │
    │                                                                │
    │  MaxSim(q2) = 0.88                                             │
    └────────────────────────────────────────────────────────────────┘

    Query token "erosion" (q3):
    ┌────────────────────────────────────────────────────────────────┐
    │  sim(q3, d1) = 0.05  (The)                                     │
    │  sim(q3, d2) = 0.25  (bank) ← Some similarity                  │
    │  sim(q3, d3) = 0.03  (of)                                      │
    │  sim(q3, d4) = 0.04  (the)                                     │
    │  sim(q3, d5) = 0.31  (river) ← Some similarity                 │
    │  sim(q3, d6) = 0.07  (was)                                     │
    │  sim(q3, d7) = 0.42  (muddy) ◄── MAXIMUM! (mud ≈ erosion)      │
    │                                                                │
    │  MaxSim(q3) = 0.42                                             │
    └────────────────────────────────────────────────────────────────┘

    STEP 2: Sum all MaxSim scores
    ┌────────────────────────────────────────────────────────────────┐
    │                                                                │
    │  FINAL SCORE = MaxSim(q1) + MaxSim(q2) + MaxSim(q3)            │
    │              = 0.91 + 0.88 + 0.42                              │
    │              = 2.21                                            │
    │                                                                │
    └────────────────────────────────────────────────────────────────┘

    This score is compared across all documents to rank them!
💡 Why MaxSim Works So Well

MaxSim ensures that every query term finds its best match in the document. Even if a document doesn't contain the exact word "erosion", it might have related words like "muddy" or "sediment" that score highly. Traditional embeddings might miss this because they average everything into one vector.

Late Interaction: Why It's Called That

Interaction Type When Query-Doc Interact Example Speed Accuracy
No Interaction Never (just cosine of pooled vectors) Sentence Transformers Fastest Baseline
Early Interaction During encoding (concatenate Q+D, run through BERT) Cross-Encoders Very Slow Highest
Late Interaction After encoding (MaxSim on precomputed embeddings) ColBERT Fast High

ColBERT is called "Late Interaction" because:

  1. Documents are pre-encoded into token matrices (can be done offline)
  2. Queries are encoded at search time (fast, single pass)
  3. Interaction (MaxSim) happens LATE — after both are encoded

This is the sweet spot: you get the accuracy benefits of fine-grained interaction without the speed penalty of cross-encoders.

ColBERT as a Re-ranker

A powerful pattern: use fast traditional embeddings for initial retrieval, then use ColBERT to re-rank the top candidates.

Python - ColBERT Re-ranking 
from ragatouille import RAGPretrainedModel
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

# Stage 1: Fast retrieval with traditional embeddings
vectorstore = Chroma.from_texts(
    texts=documents,
    embedding=OpenAIEmbeddings()
)
initial_results = vectorstore.similarity_search(query, k=20)

# Stage 2: Re-rank with ColBERT
RAG = RAGPretrainedModel.from_pretrained("colbert-ir/colbertv2.0")

reranked = RAG.rerank(
    query=query,
    documents=[doc.page_content for doc in initial_results],
    k=5  # Return top 5 after re-ranking
)

# Result: Fast initial retrieval + High accuracy re-ranking
⚠️ ColBERT Storage Considerations

ColBERT stores one vector per token (not per document). A 300-token document requires 300 vectors! For 1 million documents averaging 200 tokens each, that's 200 million vectors to store.

Solution: ColBERTv2 uses residual compression to reduce storage by ~16x while maintaining accuracy.

Key Takeaways

🎯 Summary: The Three Pillars of Advanced Indexing

  1. Multi-Representation (Part 12): Decouple what you search from what you return. Use optimized representations (summaries/propositions) for search, but give the LLM full documents for context.
  2. RAPTOR (Part 13): Build a knowledge hierarchy through recursive clustering and summarization. Answer both specific AND thematic questions from the same index.
  3. ColBERT (Part 14): Use token-level embeddings for fine-grained matching. Best for semantic precision where single-vector embeddings lose nuance.

Remember: These techniques can be combined! Start simple (Parent Document), add complexity (RAPTOR for themes, ColBERT for re-ranking) as your use case demands.
