01 The Retrieval Quality Problem

Basic RAG retrieval has a fundamental limitation: semantic similarity doesn't always mean relevance. Just because two pieces of text are "similar" in vector space doesn't mean one actually answers the other's question.

📚 Analogy: The Library Catalog Problem

Imagine you're looking for a book about "Apple's business strategy." A basic library catalog might return books about fruit cultivation, apple pie recipes, and the company Apple Inc. — all contain the word "apple" and might even discuss "strategy" (growing strategies, cooking strategies). But only one is what you actually need. Similarity ≠ Relevance.

02 RAG-Fusion & Reciprocal Rank Fusion

RAG-Fusion addresses the vocabulary mismatch problem by generating multiple query variations and then fusing the results using Reciprocal Rank Fusion (RRF).

📚 Analogy: The Hiring Committee

Imagine you're hiring a software engineer. Instead of having just one interviewer, you have five interviewers who each evaluate candidates differently — one focuses on coding, one on system design, one on culture fit, etc. A candidate who ranks highly across multiple interviewers is more likely to be a great hire than someone who aced just one interview. RAG-Fusion uses this same "wisdom of crowds" approach.

The RRF Formula Explained

Reciprocal Rank Fusion Formula
RRF(d) = Σ 1/(k + rank(d))
k = constant (typically 60) — prevents high ranks from dominating
rank(d) = position of document d in each query's results
Σ = sum across all queries where document appears

Why k = 60?

The constant k=60 is empirically chosen to balance contributions:

Rank Score (k=60) Score (k=1) Effect
1 0.0164 0.500 With k=60, rank 1 isn't overwhelmingly dominant
2 0.0161 0.333 Close scores allow lower ranks to contribute
10 0.0143 0.091 Rank 10 still has meaningful contribution
💡 Key Insight

RRF rewards consistency over dominance. A document that appears in the top 5 of ALL queries will outscore one that's #1 in one query but absent from others. This naturally filters out "false positive" matches.

🎯 When RAG-Fusion Shines

RAG-Fusion works best when your problem is vocabulary diversity — users describe things differently than your documents do. By generating multiple query perspectives, you cast a wider net and catch relevant documents that use different terminology.

03 Cohere Re-Rank: Cross-Encoder Power

While RAG-Fusion is algorithmic, Cohere Re-Rank uses a neural model (cross-encoder) to deeply understand the relationship between query and document.

📚 Analogy: ATS vs Human Recruiter

Think of basic vector search like an Applicant Tracking System (ATS) that keyword-matches resumes. It's fast but shallow — it might reject a perfect candidate because they used "Software Developer" instead of "Software Engineer." Cohere Re-Rank is like a human recruiter who actually reads and understands both the job description and the resume together, catching nuanced matches the ATS missed.

Cross-Encoder vs Bi-Encoder

📊 Architectural Difference
┌─────────────────────────────────────────────────────────────────────────────────┐ │ BI-ENCODER (Vector Search) │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ │ │ Query Document │ │ │ │ │ │ ▼ ▼ │ │ ┌────────────┐ ┌────────────┐ │ │ │ Encoder │ │ Encoder │ (Same or different model) │ │ └─────┬──────┘ └─────┬──────┘ │ │ │ │ │ │ ▼ ▼ │ │ [0.2, -0.5, ...] [0.3, -0.4, ...] ← Separate embeddings │ │ │ │ │ │ └──────────┬──────────────────────┘ │ │ │ │ │ ▼ │ │ Cosine Similarity = 0.85 │ │ │ │ ✅ FAST: Embeddings computed once, stored in vector DB │ │ ❌ SHALLOW: No cross-attention between query and document │ │ │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ CROSS-ENCODER (Cohere Re-Rank) │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ │ │ Query + Document (concatenated) │ │ ┌─────────────────────────────────────────┐ │ │ │ [CLS] What are SLA remedies? [SEP] │ │ │ │ In case of breach, Customer may... │ │ │ └────────────────────┬────────────────────┘ │ │ │ │ │ ▼ │ │ ┌──────────────────┐ │ │ │ Cross-Encoder │ ← Full attention between ALL tokens │ │ │ (Transformer) │ │ │ └────────┬─────────┘ │ │ │ │ │ ▼ │ │ Relevance Score = 0.92 │ │ │ │ ✅ DEEP: Query tokens can attend to document tokens directly │ │ ❌ SLOW: Must run model for every query-document pair │ │ │ └─────────────────────────────────────────────────────────────────────────────────┘

Why Cross-Encoders Are More Accurate

Aspect Bi-Encoder Cross-Encoder
Attention Query attends only to itself; Doc attends only to itself Query tokens can attend to document tokens and vice versa
Context Fixed embedding regardless of query Understanding changes based on specific query
Example "Bank" gets same embedding for river bank or financial bank Cross-encoder can see "SLA" in query and understand "breach" relates to it
Speed ~1ms per query (pre-computed embeddings) ~50-100ms per document pair
Accuracy Good (85-90% typical) Excellent (95%+ typical)
💡 The Deep Understanding Difference

Consider the query "What happens if the vendor fails to meet SLA?" and a document saying "In the event of service level breach, Customer may terminate." A bi-encoder might miss this because "fails to meet SLA" and "service level breach" are different phrases. A cross-encoder sees them together and understands they mean the same thing in context.

04 Two-Stage Retrieval Architecture

Since cross-encoders are slow, you can't run them on your entire database. The solution is a two-stage architecture that combines the speed of bi-encoders with the accuracy of cross-encoders.

📊 Two-Stage Retrieval Pipeline
┌─────────────────────────────────────────────────────────────────────────────────┐ │ TWO-STAGE RETRIEVAL ARCHITECTURE │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ │ │ User Query: "What are the payment terms for enterprise contracts?" │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────────┐ │ │ │ STAGE 1: BROAD RETRIEVAL (Bi-Encoder) │ │ │ │ │ │ │ │ • Use vector search for SPEED │ │ │ │ • Cast wide net (retrieve 20-100 candidates) │ │ │ │ • Goal: HIGH RECALL (don't miss relevant docs) │ │ │ │ • Cost: FREE (just vector similarity) │ │ │ │ • Time: ~50ms │ │ │ │ │ │ │ │ Output: 50 potentially relevant documents │ │ │ └─────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────────┐ │ │ │ STAGE 2: PRECISION RERANKING (Cross-Encoder) │ │ │ │ │ │ │ │ • Use Cohere Re-Rank for ACCURACY │ │ │ │ • Score each of 50 candidates against query │ │ │ │ • Goal: HIGH PRECISION (rank best docs first) │ │ │ │ • Cost: ~$0.005 (50 documents × $0.0001/doc) │ │ │ │ • Time: ~500ms │ │ │ │ │ │ │ │ Output: Top 5 most relevant documents │ │ │ └─────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ LLM Generation with Top 5 Docs │ │ │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ WHY NOT JUST COHERE ON EVERYTHING? │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ │ │ Your database: 100,000 documents │ │ │ │ OPTION A: Cohere on ALL documents │ │ • 100,000 API calls per search │ │ • Cost: ~$10 per search │ │ • Latency: 30+ seconds │ │ • Result: ❌ Impractical │ │ │ │ OPTION B: Two-Stage (Vector + Cohere) │ │ • Stage 1: Vector search returns 50 candidates (FREE, ~50ms) │ │ • Stage 2: Cohere on 50 documents (~$0.005, ~500ms) │ │ • Result: ✅ Fast, affordable, accurate │ │ │ └─────────────────────────────────────────────────────────────────────────────────┘
📚 Analogy: Job Application Funnel

Think of hiring for a job. Stage 1 is the ATS that quickly filters 1000 applications down to 50 based on keywords (fast, cheap, imperfect). Stage 2 is human recruiters carefully reading those 50 resumes (slow, expensive, accurate). You wouldn't have humans read all 1000, but you also wouldn't hire based only on ATS scores.

Tuning the Two Stages

Parameter Stage 1 (Vector) Stage 2 (Rerank) Trade-off
Documents 20-100 Top 3-5 final More Stage 1 = better recall, higher Stage 2 cost
Threshold Low (0.5 similarity) High (0.7+ relevance) Lower Stage 1 threshold catches edge cases
Latency Budget ~50-100ms ~300-800ms Most latency should be in Stage 2 (accuracy)

🎯 Combining Both for Maximum Quality

For high-stakes applications (healthcare, legal, finance), use both approaches in sequence: RAG-Fusion expands your query to catch documents using different terminology, RRF fuses the results, then Cohere Re-Rank adds precision by deeply understanding which results actually answer the question.

06 CRAG: Corrective RAG Introduction

Reranking solves the "wrong order" problem, but what if your documents are simply wrong, outdated, or missing? That's where Corrective RAG (CRAG) comes in — it doesn't just reorder documents, it grades them and finds alternatives if needed.

📚 Analogy: The Smart Research Assistant

Imagine asking a research assistant to find information on a topic. A basic assistant just hands you whatever they found in the filing cabinet. A CRAG-like assistant first evaluates what they found ("Is this actually relevant? Is it up to date?"), and if the documents are lacking, proactively searches elsewhere (the internet, other databases) to fill the gaps.

CRAG's Core Insight

🎯 The "C" in CRAG: Corrective

CRAG's key innovation is adding a grading step between retrieval and generation. Instead of blindly trusting whatever the vector search returns, CRAG asks: "Are these documents actually useful for answering this question?" If not, it takes corrective action — either filtering out bad documents or fetching alternatives from the web.

Component 3: Query Transformation

When web search is needed, CRAG transforms the query to be more effective for web search:

💡 Why Transform Queries?

Internal knowledge base queries are often different from web search queries. "How do I integrate your API with Salesforce?" becomes "[Company Name] API Salesforce integration guide 2024" — adding company name (your KB doesn't need it), year (for recency), and web-friendly keywords.

Original Query (KB) Transformed Query (Web) Why Transform?
"password reset" "[App Name] password reset guide 2024" Add app name, recency
"pricing" "[Company] pricing plans enterprise cost" Add company, specificity
"API rate limits" "[API Name] rate limits documentation current" Add API name, freshness
